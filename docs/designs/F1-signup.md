# F1 회원 가입·본인 확인 기능 설계

## 1. 목적과 범위

개인 고객이 회원 가입을 신청하고, 외부 본인 확인 기관을 거쳐 본인 확인을 마치면 고객 계정을 쓸 수 있게 한다. 가입한 고객과 직원은 같은 로그인 기능으로 로그인·로그아웃한다.

대상: 회원 가입 신청, 본인 확인 요청, 본인 확인 완료, 로그인, 로그아웃.
범위 밖: 직원 계정 생성, 비밀번호 변경(F2), 아이디·비밀번호 찾기, 계정 잠금 해제(F3, 일괄 처리).

엔티티·필드·상태 이름은 `spec/data-model.md`를 따른다.

## 2. 참여자와 역할

| 참여자 | 할 수 있다 | 할 수 없다 |
|---|---|---|
| 가입 신청자(로그인 전) | 가입 신청, 본인 확인 요청·완료 | 역할·계정 상태 지정, 다른 가입 신청의 본인 확인 진행 |
| `CUSTOMER`, `CONSULTANT`, `BILLING_OPERATOR`, `ADMIN` | 본인 계정으로 로그인·로그아웃 | `ACTIVE`가 아닌 계정으로 로그인 |
| 외부 본인 확인 기관 | 본인 확인 결과 발급. 서버의 결과 확인 요청에 응답 | 계정 상태를 직접 변경 |
| `SYSTEM`(일괄 처리) | 잠금 시간이 지난 `LOCKED` 계정을 `ACTIVE`로 해제 | 회원 가입 처리, 역할 부여 |

- 회원 가입으로는 `CUSTOMER` 계정만 생긴다.
- 로그인 후 신원·역할·계정 상태는 서버에 저장된 값으로만 판단한다.

## 3. 주요 자산

| 자산 | 등급 | 비고 |
|---|---|---|
| `resident_reg_no` | G1 | 암호화해 저장. 응답에 원문을 담지 않는다 |
| 비밀번호, `password_hash` | G3 | 원래 값을 되살릴 수 없는 형태로만 저장. 어떤 응답에도 담지 않는다 |
| `name`, `birth_date`, `phone`, `email`, `address` | G4 | 가입 신청 시 입력 |
| `login_id` | — | 전체 계정에서 유일 |
| `Account.role`, `Account.status` | — | 서버가 정한다 |
| `failed_login_count`, `identity_verified_at`, `last_login_at` | — | 서버가 기록한다 |
| 가입 신청 참조값 `signup_ref` | — | 로그인 전 가입 신청을 가리키는 값. 서버가 발급하고 추측할 수 없어야 한다 |
| 본인 확인 요청 `IdentityVerification`(`verification_id`, 기관 결과 참조값 `agency_result_ref`, `status`, `expires_at`) | — | 한 가입 신청에 묶인다 |
| 로그인 상태 | — | 서버가 확인한 계정 하나에 묶인 인증 정보. 쿠키로 전달한다 |

## 4. API

### 4.1 회원 가입 신청

`POST /api/v1/signup`

- 호출: 로그인하지 않은 사용자.
- 입력: `login_id`, `password`, `name`, `birth_date`, `resident_reg_no`, `phone`, `email`, `address`.
- 해야 할 일:
  - `Customer` 한 건과 그에 연결된 `Account` 한 건을 만든다.
  - `role`은 `CUSTOMER`, `status`는 `PENDING_VERIFICATION`, `failed_login_count`는 0으로 서버가 정한다.
  - `account_id`, `customer_id`, `created_at`, `signup_ref`는 서버가 만든다.
  - 비밀번호는 복원 불가 형태로, `resident_reg_no`는 암호화해 저장한다.
- 하면 안 되는 일:
  - 요청에 담긴 `role`, `status`, `account_id`, `customer_id`, `credit_status`, `collection_status`, `assigned_consultant_id`, `identity_verified_at`을 저장하거나 판단에 쓰는 것.
  - `login_id`가 이미 있으면 계정을 만들지 않는다. 거부 응답에 기존 계정의 정보를 담지 않는다.
- 입력 항목 외의 값이 요청에 있으면 가입 신청을 거부하고(400) 계정을 만들지 않는다.
- 응답: `signup_ref`, `status`(`PENDING_VERIFICATION`). 입력한 G1·G3 값을 되돌려 주지 않는다.

### 4.2 본인 확인 요청

`POST /api/v1/signup/identity-verifications`

- 호출: 로그인하지 않은 사용자.
- 입력: `signup_ref`.
- 해야 할 일: `signup_ref`가 가리키는 계정이 `PENDING_VERIFICATION`일 때만 외부 본인 확인 기관에 확인 요청을 만들고 `verification_id`와 기관 화면 이동 주소 `redirect_url`을 돌려준다.
- 하면 안 되는 일: 다른 상태 계정에 확인 요청을 만드는 것. 응답에 가입 신청 정보(G1·G4)를 담는 것.
- 이미 본인 확인을 마친 계정의 `signup_ref`로 요청하면 거부한다(409).
- 확인 요청은 운영 정책으로 정한 유효 시간(기본 10분, `spec/domain.md` 4장) 안에서만 완료할 수 있다.

### 4.3 본인 확인 완료

`POST /api/v1/signup/identity-verifications/{verification_id}/complete`

- 호출: 로그인하지 않은 사용자(기관 화면에서 돌아온 가입 신청자).
- 입력: 경로의 `verification_id`, 본문의 `agency_result_ref`.
- 해야 할 일:
  - 서버가 외부 본인 확인 기관에 `agency_result_ref`의 결과를 직접 확인한다.
  - 결과가 성공이고, 그 결과가 이 `verification_id`에 대해 발급된 것이며, 확인된 이름·생년월일·주민등록번호가 해당 가입 신청의 값과 같을 때만 계정을 `ACTIVE`로 바꾸고 `identity_verified_at`을 기록한다.
- 하면 안 되는 일:
  - 요청에 담긴 확인 완료 표시, 이름, 생년월일, 주민등록번호, 결과 코드를 판단에 쓰는 것.
  - 이미 쓴 결과, 다른 확인 요청의 결과, 유효 시간이 지난 요청으로 계정을 `ACTIVE`로 바꾸는 것.
- 이미 완료(`COMPLETED`)된 `verification_id`로 완료를 다시 요청하면 거부한다(409). 계정 상태와 확인 요청 기록은 바뀌지 않는다.
- 응답: `status`. 실패하면 계정 상태는 `PENDING_VERIFICATION`으로 남는다.

### 4.4 로그인

`POST /api/v1/auth/login`

- 호출: 로그인하지 않은 사용자.
- 입력: `login_id`, `password`.
- 해야 할 일:
  - `ACTIVE` 계정이고 비밀번호가 맞을 때만 로그인 상태를 만들고 쿠키로 전달한다.
  - 성공하면 `failed_login_count`를 0으로, `last_login_at`을 현재 시각으로 기록한다.
  - 비밀번호가 틀리면 `failed_login_count`를 1 올린다. 정책 횟수(기본 연속 5회, `spec/domain.md` 4장)에 이르면 계정은 `LOCKED`가 된다.
- 하면 안 되는 일:
  - 아이디가 없는 경우, 비밀번호가 틀린 경우, 계정이 `ACTIVE`가 아닌 경우를 응답 내용·상태 코드로 구분해 알려 주는 것.
  - 요청에 담긴 역할·계정 상태·계정 식별자를 로그인 상태에 반영하는 것.
- 응답: `account_id`, `role`. `password_hash`와 G1 값을 담지 않는다.

### 4.5 로그아웃

`POST /api/v1/auth/logout`

- 호출: 로그인한 사용자.
- 해야 할 일: 요청한 계정의 기존 로그인 상태를 모두 끝낸다.
- 하면 안 되는 일: 다른 계정의 로그인 상태를 끝내는 것.

### 4.6 비밀번호 재설정 요청

`POST /api/v1/auth/password-reset/requests`

- 호출: 누구나(로그인 전).
- 입력: `login_id`.
- 해야 할 일: `ACTIVE`인 고객 계정이면 재설정 토큰을 만들어 그 고객의 이메일로 보낸다(서버에는 토큰을 되살릴 수 없는 형태로만 남긴다). 새 토큰을 만들 때 그 계정의 이전 미사용 토큰은 모두 쓸 수 없게 한다. 같은 계정에 1시간 5회(운영 정책)를 넘는 요청은 토큰도 이메일도 만들지 않는다(응답은 같다). 요청만으로는 계정의 기존 로그인 상태를 끝내지 않는다. 토큰의 유효 시간은 30분(운영 정책)이다. 요청은 감사 기록에 남긴다. 응답은 계정이 있든 없든, 어떤 상태든 같은 `202`와 빈 본문이고 처리 시간도 같다(최소 응답 시간 적용).
- 하면 안 되는 일: 응답이나 상태 코드, 응답 시간으로 계정 존재 여부·상태를 알려 주는 것. 토큰 원문을 이메일 외의 응답·저장·기록에 남기는 것.

### 4.7 비밀번호 재설정 확인

`POST /api/v1/auth/password-reset/confirm`

- 호출: 누구나(로그인 전).
- 입력: `token`, `new_password`(8자 이상, UTF-8 72바이트 이하).
- 해야 할 일: 토큰이 유효하고 아직 쓰지 않았고 유효 시간 안이며 그 계정이 `ACTIVE`일 때만 비밀번호를 바꾸고, 토큰을 쓴 것으로 표시하고, 확인 시점에 그 계정에 있는 모든 로그인 상태(재설정 요청 뒤에 만든 것 포함)를 끝낸다. 계정 상태 때문에 거부되는 경우에도 토큰은 쓴 것으로 표시한다. 성공은 감사 기록에 남긴다. `204`.
- 하면 안 되는 일: 쓴 토큰·유효 시간이 지난 토큰·없는 토큰으로 비밀번호를 바꾸는 것(이유를 구분하지 않고 `400`). 새 비밀번호 원문을 응답·저장·운영 기록에(성공·실패 모두) 남기는 것.

## 5. 데이터 처리 흐름

1. 가입 신청자가 가입 정보를 보낸다.
2. 서버는 입력 형식과 `login_id` 중복을 확인한다.
3. 서버는 `CUSTOMER`·`PENDING_VERIFICATION` 계정과 고객 정보를 저장하고 `signup_ref`를 돌려준다.
4. 가입 신청자가 `signup_ref`로 본인 확인을 요청한다.
5. 서버는 기관에 확인 요청을 만들고 `verification_id`와 이동 주소를 돌려준다.
6. 가입 신청자가 기관 화면에서 본인 확인을 마치고, 기관이 발급한 `agency_result_ref`를 서버에 보낸다.
7. 서버는 기관에 결과를 직접 확인하고, 결과의 대상자와 가입 신청 값을 대조한다.
8. 일치하면 계정을 `ACTIVE`로 바꾼다. 일치하지 않으면 상태를 바꾸지 않는다.
재설정:

1. 고객이 `login_id`로 재설정을 요청한다. 서버는 `ACTIVE` 고객 계정이면 토큰을 만들어 이메일로 보내고 해시만 저장한다. 응답은 항상 같다.
2. 고객이 이메일의 토큰과 새 비밀번호를 보낸다.
3. 서버는 토큰 해시로 기록을 찾고, 쓰지 않았고 유효 시간 안일 때만 쓴 것으로 표시한다.
4. 서버는 새 비밀번호를 해시로 저장하고 기존 로그인 상태를 끝낸다. 성공을 감사 기록에 남긴다.

가입·로그인:

9. 고객이 로그인하면 서버는 계정 상태와 비밀번호를 확인해 로그인 상태를 만든다.
10. 이후 요청에서 서버는 로그인 상태가 가리키는 계정의 저장된 역할·상태로 권한을 판단한다.

## 6. 업무 불변조건

1. 회원 가입으로 만들어진 계정의 `role`은 항상 `CUSTOMER`다.
2. 가입 직후 계정의 `status`는 `PENDING_VERIFICATION`이다. 요청 값으로 다른 상태의 계정을 만들 수 없다.
3. `account_id`, `customer_id`, `role`, `status`, `failed_login_count`, `identity_verified_at`, `credit_status`, `collection_status`, `assigned_consultant_id`는 서버가 정한다. 요청에 담긴 값은 저장하지도, 판단에 쓰지도 않는다.
4. `login_id`는 전체 계정에서 유일하다. 중복으로 거부한 응답에 기존 계정의 정보를 담지 않는다.
5. 비밀번호는 원래 값을 되살릴 수 없는 형태로만, `resident_reg_no`는 암호화해 저장한다.
6. 어떤 응답에도 비밀번호, `password_hash`, `resident_reg_no` 원문을 담지 않는다.
7. 운영 기록과 오류 응답에 비밀번호와 `resident_reg_no` 원문을 남기지 않는다.
8. `PENDING_VERIFICATION` → `ACTIVE` 전이는 서버가 외부 본인 확인 기관에 직접 확인한 결과가 성공일 때만 일어난다. 클라이언트가 보낸 확인 완료 표시나 결과 값으로는 일어나지 않는다.
9. 본인 확인 결과의 이름·생년월일·주민등록번호가 가입 신청 값과 다르면 계정을 `ACTIVE`로 바꾸지 않는다.
10. 본인 확인 결과 하나는 그 결과를 요청한 `verification_id` 하나에 한 번만 쓴다. 유효 시간이 지난 확인 요청은 완료할 수 없다.
11. 본인 확인 요청·완료는 `PENDING_VERIFICATION` 계정에만 적용된다. 다른 상태의 계정은 바뀌지 않는다.
12. `ACTIVE` 계정만 로그인할 수 있다. `PENDING_VERIFICATION`, `LOCKED`, `SUSPENDED`, `DELETED` 계정의 로그인은 거부한다.
13. 로그인 실패 응답은 아이디 없음, 비밀번호 불일치, 계정 상태 사유를 응답 내용·상태 코드로 구분하지 않는다.
14. 비밀번호가 틀릴 때마다 `failed_login_count`가 1 오르고, 정책 횟수에 이르면 계정은 `LOCKED`가 된다. 로그인에 성공하면 0이 된다.
15. 로그인 상태는 서버가 확인한 계정 하나에 묶인다. 이후 요청의 신원·역할·계정 상태는 요청 값이 아니라 서버 저장값으로 판단한다.
16. 로그아웃하면 그 계정의 기존 로그인 상태는 모두 끝난다.
17. 비밀번호 재설정 요청의 응답은 계정이 없을 때, `ACTIVE`가 아닐 때, 직원 계정일 때, 성공했을 때 모두 같다(상태 코드·본문).
18. 재설정 토큰은 서버가 추측할 수 없는 값으로 만들고, 서버에는 원래 값을 되살릴 수 없는 형태로만 저장한다. 토큰 원문은 이메일 밖의 어떤 응답·저장 기록(DB, 감사 기록)·운영 기록에도 남기지 않는다.
19. 재설정 토큰은 한 번만 쓸 수 있고 유효 시간(30분)이 지나면 쓸 수 없다. 쓸 수 없는 토큰은 이유를 구분하지 않고 거부하며 비밀번호를 바꾸지 않는다.
20. 재설정에서 받은 새 비밀번호 원문은 성공·실패 경로 모두에서 어떤 응답·저장·운영 기록에도 남기지 않는다.
21. 재설정에 성공하는 시점(확인 시점)에 그 계정의 모든 로그인 상태가 끝난다. 재설정 요청 뒤에 새로 만든 로그인 상태도 포함한다. 재설정 요청만으로는 기존 로그인 상태를 끝내지 않는다(남이 요청만으로 계정을 로그아웃시킬 수 없다).
22. 재설정은 `ACTIVE` 고객 계정에만 적용된다. 그 밖의 상태에서는 토큰이 만들어지지 않고, 확인 시점에 상태가 `ACTIVE`가 아니면 거부한다.
23. 새 재설정 요청이 토큰을 만들면 그 계정의 이전 미사용 토큰은 모두 쓸 수 없게 된다(한 계정에 유효한 토큰은 최대 하나다. 시간에 상관없이 이전 토큰이 모두 무효다).
24. 같은 계정에 대한 재설정 요청은 1시간에 5회까지만 토큰과 이메일을 만든다. 한도를 넘는 요청도 응답은 같고 토큰도 이메일도 만들지 않는다.
25. 재설정 확인이 계정 상태(`ACTIVE`가 아님) 때문에 거부되어도 그 토큰은 쓴 것으로 처리되어, 이후 계정 상태가 바뀌어도 쓸 수 없다.
26. 재설정 요청의 처리 시간은 계정이 없을 때, `ACTIVE`가 아닐 때, 성공했을 때 모두 눈에 띄게 다르지 않다. 이메일 발송 같은 시간이 걸리는 일은 응답 시간에 드러나지 않도록 모든 경로가 같은 최소 응답 시간(운영 정책, 300밀리초)에 맞춘다. 판정은 같은 조건의 요청을 여러 번 보내 중앙값을 비교한다(차이 60밀리초 이내).
